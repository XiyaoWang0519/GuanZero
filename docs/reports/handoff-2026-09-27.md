## 下一步：本地吞吐量优化

- **工作目录：** 在 git worktree `/Users/xiyaowang/Developer/Projects/GuanZero-throughput` 里做，分支 `throughput-2026-09-27`，基于 `42f70a4`。里面已复制 Python 3.12 的 `gd` 扩展，引擎摘要 `606ff1e7…`，相关测试通过。Python 环境仍用主仓库的 `.work/external/danlm-venv`，运行时设 `PYTHONPATH=python:oracle:.`。
- **不要在主目录 `GuanZero` 里切分支或改代码**，因为 2×2 评估还在用那里的代码。
- **基准版本：** `42f70a4`。吞吐量改动要和它比较，证明结果逐位相同。

- **目标：** 每次决策的主机端开销降低 5–10 倍。目前每组约 400 决策/秒，瓶颈在 CPU 端。
- **本地做：**
  - 减少每步的 Python 主机工作，包括历史拼接、候选编码和数据搬运；
  - 更大的批量推理，跨环境、跨策略身份；
  - 减少 GPU 同步，例如 `history_rollout.py` 里 `explore` 每批都做的 `behaviour_logp` / 熵 `.cpu()` 和 `float()`；
  - 多个 actor 进程。
- **先读 `comparison.json`，再决定剖析哪条路径：** 宽对手池的格子比最近池慢约 20%。同样是大模型，宽池 7.0 s/更新、最近池 5.9 s/更新；小模型宽池 6.4 s/更新、最近池约 5 s/更新。一个可能的原因是每步涉及的策略身份更多，推理批次更碎。如果长跑要用宽池，跨身份批量推理的重要性会大很多。
- **Vast 报价里的 "24.0/192 CPU" 只是列表显示，不等于硬性的 cgroup 配额。** 保留"可用 CPU ≥ 16"的检查，第一次租用时看 `setup-host-facts.json` 核实。
- **约束：** 优化必须保持结果逐位相同或同分布，不允许降低精度（见记忆 no-quality-compromise-for-speed）。最终数字要在固定的 Vast 机器上测：同一台机器、稳定阶段、逐项开关。
