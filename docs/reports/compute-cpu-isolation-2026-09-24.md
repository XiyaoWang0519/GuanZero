# 算力平台补充调研：CPU 隔离（2026-09-24）

这份报告补充 [compute-options.md](compute-options.md)（09-22），只增加一个维度：分给我们的 CPU 是不是真的专属，会不会被别的租户抢。价格都是 09-24 在官网或公开 API 上查的，**都还没有实测吞吐**。

## 先修正需求

按今天的测量（[COMPUTE_GUIDE](../COMPUTE_GUIDE.md)、[perf-gpu](perf-gpu-2026-09-24.md)）：

- 采集里 86% 是推理，引擎只占 3%。引擎线程从 4 加到 16，吞吐只从 49k 涨到 60k decisions/s。所以**不需要 64 核**。
- 真正怕的是另一件事：一个 Python 线程按顺序跑引擎、上传、前向和写 buffer。这个线程一被别的租户挤掉，GPU 就只能干等。

所以要找的是：**每个实验组大约 16 个专属核，而且实际配额和标称一致**。

### 波动从哪来

| 现象 | 数据 | 性质 |
|---|---|---|
| 同样的代码换一台机器 | 27,894–40,803 decisions/s | 主机之间差异很大 |
| 同一台机器上交替跑 ABBA | 31k–57k | 同一台机器内部也在漂 |
| overnight control 这一轮，每次 update 的采集时间 | 按 100 次 update 分段取中位数：从 2.02 s 逐步升到 2.96 s，之后一直稳定在 2.95–2.98 s | 是训练本身的趋势（对局变长），**这台机器上没看到被抢的迹象** |
| 标称 64 vCPU 的 4090 pod | 实际 cgroup 配额 13.6 和 17.85 | 标称值和实际配额对不上 |

所以主要问题是：抽到哪台机器全凭运气，而且实际配额和标称值对不上。同一台机器上也会漂（ABBA 那一行），但不是每台都这样。根源在 RunPod 的形态：它是共享主机上的 Docker 容器，靠 cgroup 限额。

- 官方文档里说的 "dedicated" 只是指 pod 不会被别人挤掉，**没有说 CPU 是独占的**（[pods pricing](https://docs.runpod.io/pods/pricing.md)）。
- 定价页只列出每张 GPU 的最低 vCPU 配置（4090 是 6 个，5090 是 9 个）。实际分到多少要看机器，也没有说明这些 vCPU 是不是专属。
- RunPod 的独立服务器（bare metal）只能找销售谈，不是按小时计费。

## 各平台的隔离情况

| 平台 | 形态 | 单卡报价（$/h） | CPU 是否专属 | 实例内能否自毁、且不放主 key | 结论 |
|---|---|---|---|---|---|
| **Vast.ai 整机** | 一台主机只有 1 张 GPU（`gpu_frac=1`），我们租下整台 | 4090 **0.47**（64 线程，EPYC 7713，可靠性 0.997）；5090 **0.60**（64 线程，EPYC 9554，0.99）、0.64（48 线程，0.997） | **整台机器没有其他 Vast 租户**；主机本身是不是虚拟机，没法确认 | 能：实例里有 `CONTAINER_API_KEY`，或用只限这一个实例 ID 的 scoped key | **首选** |
| Vast.ai 切片 | 多 GPU 主机的一部分 | 5090 从 0.48 起（1/8 台 256 线程主机） | 只保底按 GPU 比例分到的核，忙时别人也会来抢 | 同上 | 本质上和 RunPod 一样 |
| Hyperstack（CANADA-1） | 虚拟机 | A6000 0.50、L40 1.00，每卡 28 核 | 定价表的列名是 "pCPUs per GPU"，但文档没有承诺不超卖 | 休眠能停掉计算费用；**在实例里 `shutdown` 照样计费** | **备选**，按分钟计费、离得近 |
| TensorDock | KVM 虚拟机 | 4090 约 0.37，另加 vCPU 每个 0.003/h（32 vCPU 加 64 GB 约 +0.23） | 明确说 GPU 专属，**没有说 vCPU 专属** | 没有 scoped key，也没有最长运行时间设置 | 第三选择 |
| Hetzner GEX131 | 独立服务器 | 约 1.59（24 个物理核，RTX PRO 6000） | **一定专属** | 能不能用 API 下单和退订，没法确认 | 太贵，机房在欧洲 |
| Nebius / Lambda / Verda / DO / OVH / Scaleway | 虚拟机 | 1.1–1.9 | 都没有说明 | 大多数在实例里关机仍然计费 | 更贵，而且同样不保证专属 |
| AWS g6.8xlarge / GCP g2-standard-32 | 虚拟机 | 2.0 / 1.9（spot 1.2 / 1.15） | 行业惯例是专属，这次没有逐条核实 | AWS 可以设成"实例内关机即删除" | 贵，L4 也慢 |

**要点**：这些平台里，没有哪家在文档里写明"vCPU 专属、不超卖"。最便宜、最确定能拿到整机 CPU 的，是 **Vast.ai 上只有一张卡的整机**。它甚至比 RunPod 的 5090 community（0.69）还便宜。

需要注意，Vast 显示的 `cpu_cores` 是线程数，不是物理核。另外它上面很多主机是个人或小机房，要按 `reliability` 和 `verified` 筛。

## 建议的试用顺序

RunPod 还剩约 $50，按原计划先把它用完。但切换平台的准备可以现在就花几美元做掉。

1. **先把"CPU 有没有被抢"变成能测的数字。** 给 `infra/cpu_budget.py --facts` 加两项：
   - 几秒内 `/proc/stat` 里 steal 时间的增量；
   - 一个单线程 busy-loop 的耗时。

   以后在任何平台上，第一次检查就能量化 CPU 被抢的程度，不用靠猜。这一项尚未实现。
2. **在 Vast.ai 整机上跑一次 30 分钟的对照，预计不到 $1。**
   - 筛选条件：`num_gpus=1`、`gpu_frac=1`、`verified`、`reliability>=0.98`、按需实例、`cpu_cores_effective>=32`，4090 或 5090。
   - 跑 `bench/ppo_throughput.py`，重复几次，看两件事：每百万 decisions 花多少钱，以及次与次之间的方差。和 RunPod 的数据比。
   - 自毁用 scoped key（只限这一个实例 ID），接到现有的 deadline 逻辑里。`infra/runpod.py` 不支持 Vast，需要单独写一条 launch 和 guard 路径。
3. **Vast 效果不好（方差仍大，或者可用主机太少）时，改试 Hyperstack CANADA-1 的 A6000（$0.50，28 核）。** 它是虚拟机，而且在加拿大。缺点是在实例里关机不停止计费，guard 必须调用删除 API。另外，A6000 的算力比 4090 弱，要一起算进成本里。
4. **RunPod 余额用完之前，每个 pod 开机后先检查 CPU 配额**（COMPUTE_GUIDE 第 2 条）。配额远低于需要时，释放这台、重新开一台。

预期：Vast 整机能消除"别的租户抢 CPU"这一类波动，但不同主机之间 CPU 型号不同带来的差异还会有。所以配对比较的实验组仍然要放在同一台机器上，或者在报告里注明各组跑在哪台主机上。

## 未能确认

- Vast 的 `CONTAINER_API_KEY` 具体有哪些权限；Vast 主机本身是不是虚拟机、会不会超卖。
- TensorDock 单卡最多能配多少 vCPU、有没有 5090 或 L40S。
- Hyperstack 的 CPU 是否真的专属：需要开机后用第 1 步的 steal 测量来确认。
- Nebius 大规格的价格；Genesis Cloud（官网 SSL 错误，打不开）。
