# RTX 4090 profile: where a PPO step goes, and lazy opponent features

Date: September 24, 2026 (evening). Three RTX 4090 secure pods, measurement
only, about 57 minutes and $0.70 in total. Code change: `train/ppo.py`
(`RowGather`, `RolloutCollector._opponent_rows`). Test:
`tests/test_ppo_throughput.py::test_opponent_rows_gather_features_lazily_with_eager_values`.
Kit, raw results and evidence scripts: `.work/runpod-gpuopt-2026-09-24/`
(git-ignored; `results-session{1,2,3}/`, `equiv_opp.py`, `percall.py`).

Arms: `frozen` is `b9-exploit-m1-rtx4090.json` with `kl_coef 0` (so the
reference skip is live); `league` is `b11-main.json` without imports. Both
2,048 environments × 64 steps, 16 engine threads unless stated otherwise.
Bench numbers are `bench/ppo_throughput.py`, 2 warm-up plus 6 measured
updates, `--profile` off.

## Result

One new exact speedup: on the league arm, opponent features are gathered only
for the rows a network opponent reads, instead of copying float32
observations and candidates for every opponent row (greedy and styled rows
included) and then gathering the network rows again. Scripted and styled
opponents never read features.

Six alternating old/new pairs on one pod (13.6-CPU quota), league arm:

| | Old (HEAD 82176a2) | New |
|---|---:|---:|
| Decisions/s, median (max) | 66,514 (68,570) | 72,531 (73,967) |
| Collect, 6 updates, median (min) | 6.65 s (6.43) | 5.68 s (5.56) |
| Learn, 6 updates, range | 4.90–5.40 s | 4.99–5.42 s |
| `_opponent_rows`, steady profile | 2.7 ms/step | 0.13 ms/step |

Every pair favoured the new code; collect is 15% faster and the arm 9%
faster end to end. The frozen arm does not use this path (its opponent is
fused into the reference forward).

Equivalence, CPU, real checkpoints (M1 final, B8 league final, B6 DMC):
old and new trainers in one process over 4 league updates give identical
statistics, policy and critic weights, buffer arrays and progress counters
(only wall time and process RSS differ). Over 16 updates, 172 finished
matches and a full pool of 16 active models including 4 learner snapshots,
all 1,024 `_opponent_rows` calls return features equal to the eager gather,
whole and for random subsets. A longer whole-run comparison is not possible:
two runs of the *old* code in one process already diverge from update 5,
most likely because snapshot seeds hash the snapshot path, which contains
each run's temporary directory (not verified).

## Where a steady step goes on CUDA

Steady state means four full updates first; the earlier profile window,
right after two short warm-ups, showed first-round and first-touch
artifacts (for example `_opponent_rows` at 16 ms/step) and was discarded.
From the steady profiles (`profile_collect.py`, no phase synchronisation):

| | Frozen (pod 2) | League, old code (pod 2 / pod 3) |
|---|---:|---:|
| Collect step, plain | 14.8 ms | 18.9 / 17.1 ms |
| GPU busy during collect | 40% | 36% / 43% |
| Kernel launches per step | 281 | 342 |
| Largest host item | engine `pending`, 4.4 ms | `pending` 4.3 ms, `_opponent_rows` 4.7 / 2.7 ms |
| GPU busy during learn | 53%¹ | 57%¹ / 55% |

Pod 2 had a 31-CPU quota, pod 3 a 13.6-CPU quota (so its 16 engine threads
oversubscribed; the old/new pairs on it are still comparable). ¹ Pod 2's
profiles ran the tree with the pinned-staging change that was later
rejected (below); it affects only `stage` inside learn.

`pending` already runs on the engine's thread pool; the remaining host
items are buffer writes (about 1.4 ms/step), uploads and launch overhead.
Collect and learn took about equal time per update on these hosts.

## Other measurements

- `learn_on_device` (committed in fad2d9b), first pod, best learner step
  of three runs each: frozen 18.9 ms with it against 28.2 ms without,
  league 29.6 against 33.7 ms (about 12%). Host noise is large (below), so
  these are minimums, not medians.
- `skip_unpruned_reference`: no measurable collect change on the GPU.
- Actor processes, first pod (31-CPU quota), 4 engine threads per actor:
  four actors cut collect 1.4–1.8× (frozen 5.25–6.2 → 3.8 s, league
  7.4–7.9 → 4.35–4.8 s per 6 updates). End to end the frozen arm went from
  76k to 99k decisions/s without MPS and 89k to 103k with it (1.15–1.3×),
  because learn is unchanged. Single runs, statistically equivalent rather
  than bitwise. MPS starts inside the pod (private pipe directory) but its
  effect is within noise. Two actors were mixed (worse than one on the
  frozen arm, better on the league arm), inside the learn noise.
- Host noise: identical code and optimizer-step counts gave learner steps of
  19–70 ms at a host load average near 70, and the second pod showed
  30–40 s learn outliers (6 updates) with both old and new code. Compare
  code only on one pod, alternating runs, and read medians and minimums.

## Rejected

- Reusing a pinned staging buffer in `RolloutBuffer.stage` (gather with
  `torch.index_select(out=)` into grow-only pinned memory, event-guarded):
  bitwise identical on CUDA, but in four alternating pairs the frozen learn
  took 3.4–5.3 s against 3.6–3.8 s for the old code, and the league pairs
  were too noisy to read. In steady state `stage` is a small part of learn.
- glibc malloc tuning (`MALLOC_MMAP_THRESHOLD_` 32 MB, large trim and top
  pad): league learn looked faster in two pairs, frozen collect about 10%
  slower in two pairs. Not adopted.
