# Velocity 三层解码器训练提速调查（2026-11-18）

在 22087 的实际初始化权重上，最值得开发的新优化是让采样端三层解码器复用旧公开前缀的 K/V。最值得先做 Velocity 完整 PPO 对照的已有实现是公共编码器的 Triton 分页注意力。下列本地测量全部使用冻结权重。作业 22087 查询时为 `PENDING (Resources)`，本次未提交或修改任何集群作业。

- 初始化文件从 Velocity 只读下载，SHA-256 为 `3931c4ca835fdba5b462e615b0197181ed5c1afc8f8abb40f785b0519cc6c613`。队列包源码摘要为 `9467b6ee31485cd8e191d8cf6cf6db7c385c9dbce134413db0ccb659efbefe10`。包中 50 个 `train/*.py` 范围内的 Python 文件逐字节匹配本地源码。

- 每一步由基线输出驱动环境。候选读取同批输入、使用相同的随机数检验动作。短局和长局分别覆盖 16,384 和 1,024 次环境决策。解码器数值比较只统计需要模型出牌的行。逐区块计数和计时见[原始汇总](data/velocity-sequence-throughput-2026-11-18.json)。

## 1. 给采样端解码器缓存已投影的公开历史

现有页池保存四层**公共编码器**的 K/V 和最终编码。新解码器的每一层在每次出牌时仍对整段最终编码做 `kv_proj` 和逐头 K 归一化。对同一权重和同一公开前缀，这部分只依赖已经看到的事件。座位、当前手牌、当前轮次和相对位置偏置仍照常按这次出牌计算。[页池](../../train/history_paged_cache.py) · [解码器](../../train/history_decoder.py)

原型仅作用于采样的 learner 席位。它按比赛和流版本保存三层的已归一化 K 及 V，将各桌新出现的事件合批投影，再放回原有注意力布局。对真实牌局逐步检查所有合法候选的 log 概率。

| CPU 冻结回放 | 128 桌，从开局测 | 8 桌，长前缀 |
|---|---:|---:|
| learner 出牌数 | 9,866 | 610 |
| 合法候选数 | 163,401 | 10,408 |
| learner 最长可见前缀 | 199 | 1,134 |
| 原路径每层投影行数（含填充） | 1,284,224 | 656,000 |
| 增量路径每层投影行数 | 29,339 | 12,529 |
| 实际有效位置中，来自已投影旧前缀的比例 | 96.1% | 97.2% |
| 最大候选 log 概率差 / 不同采样动作数 | 0 / 0 | 0 / 0 |
| learner 候选打分累计耗时，原版 → 原型 | 1.500 → 1.299 秒 | 0.648 → 0.446 秒 |

打分计时包括 learner 模型的解码和候选动作头。长局样本的桌数较少。短局重复回放得到相同的投影计数和数值结果。填充和旧前缀的投影行数相加可省 97.7%（128 桌），但 attention 仍要读取所有可见位置，页表索引、K/V 读取和张量搬运仍有成本。

另做一次**完整 CPU 冻结采样**对照，把环境、公开编码、快照推理、采样和 buffer 写入都计时，关闭双算核验。每次从相同权重和种子重建 128 桌，连续采样两段各 64 步，中间清空 learner 缓存。预热一次后按 ABBA、BAAB 顺序，每臂四次，每次 16,384 个环境决策。原版耗时中位数 **8.735 秒**，只改 learner 解码器后的中位数 **8.480 秒**，采样吞吐 **+3.0%**。全部试次的出牌、已存策略和行为 log 概率、前缀、所选候选及最终采样器状态摘要相同。计时不含初始化、反向传播、DDP 和存盘。

生产实现可把投影 K/V 与公共页同行存放，按权重版本、比赛流和页生命周期失效。PPO 梯度路径继续从本批公开流重算。三层新增 FP32 数据为 `3 × 2 × 128 × 4 = 3,072` 字节/位置，即 192 KiB/64 位置的页。仅给 learner 池加缓存可先限制成本。如果两个池都按现有容量分配，按 Velocity 旧主线 u234962–234993 的 rank 0 实测页数中位数 3,923.5 估算，单 rank 多约 736 MiB，尚需计入临时 gather 和扩容峰值。旧主线这 32 次更新的平均前缀中位数为 565，单次最长达 3,624。新解码器的稳态页数和 GPU 峰值需实测。[learner 缓存失效位置](../../train/history_rollout.py)

## 2. 压缩合并快照的解码器投影

合并路径把快照槽数、单个快照所占的最大桌数、最长公开流三者相乘，形成 K/V 投影的矩形。128 桌短局测到每层 2,116,837 个矩形位置。如果保留原有时间维，只为每个快照实际参与的桌做投影，可减少到 589,834 个位置，少 72.1%。此项可以单独做，也与增量缓存有重叠。[快照批次布局和解码路径](../../train/history_snapshot_batch.py)

- 按快照实际桌数分别投影的原型将快照候选打分从 2.574 秒降至 2.197 秒。6,150 次快照选择全部一致，但有 16 个候选的 log 概率绝对差大于 `2e-5`，最大 `6.10e-5`。当前快照专项测试用 `2e-5` 对比逐身份参考，此处用相同阈值比较新原型与已部署的合并路径。应先解决数值差异再考虑部署。[数值比较标准](../../tests/test_history_snapshot_batch.py)
- 更保守的原型只剔除空快照槽，保留每个活跃槽原来的矩阵形状。候选 log 概率与采样在短局完全一致，但只少做 15.7% 的投影行，打分从 2.628 秒增至 2.930 秒。GPU 上值得比较按实际桌数进行分组矩阵乘的实现，并计入整理权重、恢复行序和 kernel 启动的时间。[NVIDIA grouped GEMM 调度说明](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/grouped_scheduler.html)

## 3. 将已有的 Triton 公共分页注意力迁到 Velocity 验证

`--rollout-paged-cache` 选择分页存储，22087 的后端仍是默认的 PyTorch。仓库已有直接从页表读取 K/V 的 Triton kernel，可从 benchmark 为每个新进程显式选用。它作用在公共编码器的 rollout 前向。10 月 18 日用一张外部 L40S、随机初始化的旧架构和单进程跑完整 PPO，普通分页得到 1.40×，合并快照得到 1.39×（4,677 → 6,479 decisions/s）。现有代码和这次旧 L40S 收据让它成为开发成本最低的 Velocity 候选。此次未在新解码器、成熟权重和双卡共享拓扑上测出该收益。[10 月 18 日完整 PPO 对照](paged-attention-prototype-2026-10-18.md#l40s-measurement-october-18) · [后端选择](../../train/history_paged_attention.py)

## Velocity 对照顺序

先用 Triton 公共分页注意力对照当前 PyTorch 后端，再独立比较 learner 解码器增量 K/V。两臂使用同一 checkpoint、同一实际快照池、2 张 L40S × 每卡 4 rank、每 rank 128 桌及相同 PPO 配方。在冻结长短牌局上检查全部候选 log 概率、采样动作和 RNG，以及 PPO 重算的一致性。随后在历史填满后交替运行 A/B 与 B/A 区块，各自记录完整更新最慢 rank 的墙钟、全局 decisions/s、采样和学习耗时、峰值显存和分配重试。同步 profiler 数据单独采集。保存周期的磁盘耗时单列。分别验证通过后，组合收益需重新测量。
